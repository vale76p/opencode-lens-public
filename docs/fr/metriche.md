# Métriques

🌐 [Italiano](../metriche.md) · [English](../en/metriche.md) · Français

## Ce que signifient les chiffres

- **Step** : un appel au provider. Il correspond à un message de l'assistant ; les retries réutilisent le même ID et sont comptés comme des tentatives (`attempts`), pas comme des steps en plus.
- **Tokens** : OpenCode les normalise ainsi (vérifié sur OpenCode v2.0.26) :
  - `input` = prompt **moins** les tokens lus depuis le cache ;
  - `output` = completion **moins** le reasoning ;
  - le vrai prompt est donc `input + cache read + cache write`. Le « % cache » est `cache read / prompt`.
- **Coût** : calculé par OpenCode à partir des prix des modèles dans la configuration (par million de tokens). Le reasoning est facturé comme de l'output. Pour les modèles locaux le coût est 0, sauf si vous déclarez un prix : voir [configurazione.md](configurazione.md#prix-pour-les-modèles-locaux).
- **Tâches internes** : génération du titre, compaction et autre travail qu'OpenCode fait sans step visible. Depuis le schéma v4 (OpenCode 2.0.32) la lens les enregistre par type :
  - **title** : depuis l'événement `session.usage.recorded` avec `source: "title"`. OpenCode ne laisse aucun message pour le titre et n'indique pas quel modèle l'a généré, donc il n'existe **qu'en direct** et sans modèle ;
  - **compaction** : depuis `session.compaction.ended` (ou `failed`) en direct et depuis le message `compaction` à la lecture, avec modèle, raison (automatique ou manuelle) et usage. C'est le total des tentatives : les `usage.recorded` de la même compaction ne sont pas ajoutés une seconde fois ;
  - **other** : l'estimation habituelle, *total de la session − Σ steps − tâches internes déjà enregistrées*, comme delta avec la date de synchronisation. Elle couvre la lens éteinte ou déconnectée, les anciennes versions d'OpenCode et tout l'historique antérieur à la v4.

  Une ligne exacte qui arrive après une estimation qui la contenait déjà l'**absorbe** : Σ steps + Σ tâches internes reste égal aux totaux de la session et rien n'est compté deux fois. Le coût total de la période inclut les tâches internes ; le coût et les tokens **par modèle** (budget, tableau par dimension, tendance) non, pas même les compactions dont le modèle est connu : le détail par type et par modèle se trouve dans `/api/summary` (`internal.byKind`, `internal.byModel`).
- **Latence** : durée de la dernière tentative du step, du début à la fin. Les steps en échec ou encore en cours n'entrent pas dans les percentiles p50/p95.
- **Premier token, tok/s et queue d'outils** (depuis le schéma v4, uniquement pour les messages OpenCode de la mi-octobre 2026 en poursuivant, ceux avec `time.streamed`). Pour chaque step la lens enregistre trois instants de la dernière tentative :
  - la **requête** au provider (`data.started` de `session.step.started`, `time.created` du message) ;
  - la **première sortie** : texte, reasoning ou arguments d'un tool (`session.text.started`, `session.reasoning.started`, `session.tool.input.started`). Dans les messages seules les parties reasoning et tool ont un temps : si un step commence par du texte et que la lens ne l'a pas vu en direct, la première sortie n'est pas connue ;
  - la **fin du stream** (`session.step.streamed`, `time.streamed`). Ce n'est pas le premier token : OpenCode l'écrit quand le provider a fini de répondre, avant d'attendre les tools.

  À partir de ces trois instants : **premier token** = première sortie − requête ; **tok/s** = (output + reasoning) / (fin du stream − première sortie), uniquement pour les steps non échoués avec au moins 500 ms de stream et 20 tokens ; **queue d'outils** = fin du step − fin du stream, c'est-à-dire combien de temps le step a attendu les tools après la réponse du modèle. Une tentative répétée remet à zéro première sortie et fin du stream ; un événement de la tentative précédente est ignoré.
- **Durée d'un tool** : l'exécution seule, sans le temps que le modèle passe à écrire les arguments. Depuis la mi-octobre 2026 OpenCode enregistre le démarrage du tool (`time.ran`, événement `session.tool.called`) séparément de la création de l'appel (`time.created`, qui est désormais le début des arguments) : la lens utilise `ran`. Les données antérieures n'ont pas `ran` et leur `created` est déjà le début de l'exécution, donc pour celles-ci elle utilise `created`. Les appels encore en cours n'entrent pas dans les percentiles ; le dashboard indique sur combien d'appels la durée est calculée.
- **Raison d'interruption** : pour un run interrompu OpenCode dit pourquoi avec `session.execution.interrupted` (`user` « par vous », `superseded` « remplacé », `inactivity` « pour inactivité », `shutdown` « arrêt d'OpenCode »), mais ne l'écrit pas dans le message `idle`. La raison n'existe donc que pour les runs vus **en direct** à partir du schéma v4 ; les autres restent « interrompu ». Avec `shutdown` OpenCode n'écrit aucun `idle` : ce run reste ouvert et fusionne avec le suivant (seul le signal subsiste).
- **Run** : du prompt (message de l'utilisateur ou synthétique) à la fin de la réponse. Depuis la mi-octobre 2026 OpenCode ferme chaque run avec un message `idle` qui indique le résultat (`succeeded`, `failed`, `interrupted`) ; un prompt envoyé pendant que le run est en cours (`steer` ou `queue`) reste à l'intérieur de ce run. Pour les messages au format précédent (sans `idle`, sans `time.streamed` sur les steps) la lens déduit le run du prompt jusqu'au dernier message de l'assistant avant le prompt suivant, sans résultat (« sans résultat » ; « échoué » si le dernier step est en erreur). Le coût, les tokens et les steps d'un run incluent ceux des subagents lancés pendant le run. Seuls les runs des sessions principales sont comptés : ceux des subagents sont déjà dans le run qui les a lancés.
- **Prompts dans le dashboard** : un prompt est un **run**, du message de l'utilisateur au message `idle` qui ferme la réponse. Les messages envoyés pendant que le run est en cours restent à l'intérieur (leur nombre est `prompts` dans la liste). Seules les sessions principales comptent ; les tokens, le coût, les steps et les tools des subagents lancés pendant le run sont inclus, et les tâches internes (titres, compaction) **ne le sont pas** : elles ne figurent pas dans les tokens d'un prompt.
- **À quel prompt appartient un step ou un tool** : chaque step ou tool appartient au run si son instant (pour un tool, celui de son step) tombe dans `(fin du run précédent de la même session, fin de ce run]`, sur l'arbre des sessions. L'« interaction » (et les chiffres de `/api/activity`) utilise en revanche la fenêtre `[début, fin]` du run : entre un `idle` et le prompt suivant il n'y a pas de travail, donc les chiffres coïncident presque toujours, mais pour les anciens runs sans début ou dans des cas limites ils peuvent différer légèrement.
- **Prompt en cours** : prompts et runs ne sont écrits qu'avec la synchronisation des messages, donc le prompt en cours est reconnu à partir des steps et des tools. Il y a un prompt en cours quand la session principale a de l'activité après la fin du dernier run **et** soit un step ou un tool est en cours depuis moins de 30 minutes, soit une permission est en attente, soit le dernier step s'est terminé il y a moins de 5 minutes. Il disparaît de lui-même 1 à 2 secondes après le `idle`, quand la synchronisation écrit le run. Quand un nouveau run se ferme, le flux reçoit un événement « prompt terminé » (`kind: "run"`).
- **Remplissage du contexte** : les tokens de prompt du dernier step terminé (`input + cache read + cache write`) sur le `limit.context` du modèle. La limite vient d'abord de la configuration d'OpenCode, puis du catalogue des modèles du service (`GET /api/model`), relu au plus toutes les 10 minutes ; si elle n'est pas trouvée, le dashboard n'affiche que les tokens. Le catalogue est contrôlé comme les événements : un champ manquant apparaît parmi les API drift (dashboard, `/api/status`, `/metrics`). La variante du modèle (`#xhigh`) est ignorée dans la recherche.
- **Prompts (messages)** : messages de l'utilisateur dans les sessions principales (le prompt qu'un agent écrit pour lancer un subagent ne compte pas). Seules la longueur en caractères et le nombre de fichiers et d'agents joints sont enregistrés ; jamais le texte. « Pendant un run » désigne les prompts envoyés pendant que l'agent travaillait (`delivery: steer`), connus uniquement pour les prompts vus en direct.
- **Permissions** : demandes de permission (`permission.asked`) avec l'action (`shell`, `edit`, …) et la réponse (`once`, `always`, `reject`). L'**attente** est le temps entre la demande et la réponse : combien de temps l'agent est resté arrêté à vous attendre. OpenCode ne conserve que les permissions en attente, donc la lens ne les enregistre que pendant qu'elle tourne.
- **Commits** : `git commit` (aussi `git -C dir commit`) exécuté avec succès par un tool shell (`shell`, `bash`). La commande n'est pas enregistrée : seulement le fait que c'était un commit. Les « tokens par commit » sont le total de la période divisé par les commits.
- **Subagents** : sessions filles (`parentID`). Chaque session de subagent est liée à l'appel `task`/`subagent` qui l'a lancée ; dans les sessions la lens additionne les subagents (imbriqués compris) dans la session parente. Le « type d'agent » sépare primaires et subagents dans les graphiques et les tableaux.
- **Aujourd'hui** : le jour de budget en cours (depuis minuit, ou depuis `LENS_RESET_HOUR`), tokens (tâches internes comprises), coût et steps, par rapport aux budgets `LENS_LIMIT_TOKENS`, `LENS_LIMIT_COST`, `LENS_LIMIT_STEPS`. Les tokens du jour ont une barre avec limite, seuil de 80 % et projection ; la semaine et le mois sont dans deux mini-barres du même widget, uniquement avec les budgets `_WEEKLY` et `_MONTHLY`. Le coût et les steps n'apparaissent qu'avec un budget ; la valeur passe au jaune à 80 % et au rouge à 100 %. La projection est linéaire (usage jusqu'ici ÷ temps écoulé × 24 h) et apparaît après la première heure. La comparaison du widget Aujourd'hui utilise la moyenne des 7 jours de budget précédents **jusqu'à la même heure** de la journée (pas la moyenne de la journée entière, qui reste dans l'infobulle).
- **Calendrier** : un carré par jour sur les 53 dernières semaines, à partir du lundi, dans la métrique choisie (tokens, coût, steps). Les quatre niveaux de couleur sont les quartiles des jours actifs. La série en cours compte les jours consécutifs avec au moins un step jusqu'à aujourd'hui.
- **Jours élagués** (seulement avec `LENS_RETENTION_DAYS`) : les steps et les tools plus anciens que la rétention ne sont plus là comme lignes, mais leurs sommes par jour oui. Elles comptent dans les totaux de `/api/summary` (de « Tout » et d'une période choisie à la main qui contient leur minuit) et dans `/metrics` ; les graphiques, les répartitions, les sessions, les prompts et la latence ne montrent que les lignes conservées. Voir [Rétention des détails](configurazione.md#rétention-des-détails).
- **tok/s** dans le tableau par dimension : la médiane des tok/s des steps (voir plus haut), avec à côté le premier token médian. L'ancien « Output tok/s », output / durée totale du step avec l'attente du premier token et des tools à l'intérieur, reste dans l'API sous `outputTokensPerSec` mais n'est plus affiché.
- **Couleurs** : les 6 premiers modèles (ou agents, ou providers) par tokens *sur toute la durée* ont une couleur fixe, qui ne change pas avec la période. Les autres vont dans « autres » (gris). Les « tâches internes » sont en violet.
- **Buckets des graphiques** : à l'heure jusqu'à 2 jours, au jour jusqu'à 120 jours, à la semaine (à partir du lundi) au-delà. En heure locale. Avec `LENS_RESET_HOUR` écrit avec le `Z` final (par exemple `2Z`) le jour de budget est UTC et les étiquettes horaires sont des heures UTC. Le jour du changement d'heure l'heure doublée additionne deux heures.

## API locale

Tous les GET et tous en JSON, sauf les écritures `POST /api/settings`, `POST /api/restart`, `POST /api/modules/notice`, `POST /api/modules/check`, `POST /api/dashboard`, `POST /api/presets`, `POST /api/skills`, `POST /api/skills/<id>`, `POST /api/skill-presets`, `POST /api/skill-loads`, `POST /api/vibe-projects`, `POST /api/update` et `POST /api/update/apply`. Ils acceptent `from`/`to` en ms epoch ; `from=0` signifie « tout » et `from=day` le jour de budget en cours (depuis minuit ou depuis `LENS_RESET_HOUR`, avec `to` à la fin du jour). Sans `from` la période est la dernière semaine. Le dashboard envoie la langue et le format qu'il a résolus dans les en-têtes `X-Lens-Lang` et `X-Lens-Locale`, et les textes des réponses destinés aux personnes (erreurs, descriptions, état) les suivent ; sans les en-têtes ils sont en italien.

| `opencode_lens_bob_bobcoins_total` | counter | `kind` : Bobcoins dépensés, comme Bob les compte par tâche |
| `opencode_lens_bob_cost_usd_total` | counter | `kind` : les mêmes Bobcoins en USD, avec `LENS_BOB_COIN_USD` |
| `opencode_lens_bob_tokens_total` | counter | `type` (`input`, `output`, `cache_read`, `cache_write`) |
| `opencode_lens_bob_requests_total` | counter | `model` : appels au modèle, toujours `model="auto"` : Bob n'enregistre pas le modèle qu'il choisit |
| `opencode_lens_bob_tool_calls_total` | counter | `tool`, `status` (`completed`, `error`, `pending`) |
| `opencode_lens_skill_loads_total` | counter | `skill`, `channel` (`skill`, `activated`, `lens-preset`, `lens-prompt`), `origin` (`lens`, `native`) : chargements terminés d'une skill |
| `opencode_lens_skill_preset_loads_total` | counter | `preset`, `channel` (`lens-preset`, `lens-prompt`) : chargements terminés d'un preset |

Les compteurs n'ont que des labels qui ne changent plus : un step entre dans `opencode_lens_steps_total` quand il se termine (`finish` est la raison de fin, `unknown` si OpenCode ne la donne pas) et un appel de tool entre dans `opencode_lens_tool_calls_total` quand il est `completed` ou `error`. Jusqu'à la 0.9.0 les steps en cours étaient dans `finish="running"` et les tools en cours dans `status="pending"`/`"running"` : ces séries baissaient ou disparaissaient à la fin du step, une baisse que Prometheus lit comme un reset et que l'export OTLP `delta` comptait deux fois. Maintenant ce qui est en cours se trouve dans les gauges `opencode_lens_steps_running` et `opencode_lens_tool_calls_running` ; celui qui utilisait `finish="running"` ou `status=~"pending|running"` doit passer à celles-ci. Un step ou un appel interrompu ne reçoit jamais de fin : c'est pourquoi les deux gauges ne comptent que ceux démarrés dans les 30 dernières minutes, et ceux restés en suspens ne restent pas « en cours » pour toujours. La même fenêtre s'applique aux steps « en cours » du Résumé (`runningSteps` de `/api/summary`), aux appels ouverts de `/api/tools` (`open`) et aux steps du détail de session (`running`) : dans la timeline un step interrompu est « interrompu », pas « en cours ».

Avec `LENS_LABELS` (par exemple `host=mini,team=ai`) chaque série reçoit aussi ces labels : utile pour collecter plusieurs ordinateurs dans le même Prometheus. Un exemple d'alerte de budget :

```promql
opencode_lens_today{kind="tokens"} / on(host) opencode_lens_daily_limit{kind="tokens"} > 0.8
```

### Des compteurs qui ne baissent pas

Les counters et les summaries de `/metrics`, et donc de l'export OTLP, portent sur toute la durée et sont calculés à partir des lignes de la base. Quand la lens supprime des lignes (aujourd'hui seulement la rétention de `LENS_RETENTION_DAYS`, demain une migration) elle passe toujours par `Store.deleteCompensated` : dans la même transaction elle compare la valeur de chaque série avant et après la suppression et enregistre dans `counter_offsets` ce qu'elle a perdu, par nom et étiquettes (un summary comme `<nom>_sum` et `<nom>_count`). `/metrics` ajoute l'offset à la valeur calculée, donc :

- aucune série ne baisse à cause d'une suppression ;
- une série dont toutes les lignes ont disparu reste, avec sa dernière valeur, même si elle valait 0 (par exemple les tokens de cache d'un modèle qui n'utilise pas le cache) ;
- les nouvelles lignes s'ajoutent à l'offset comme avant.

Sans rétention `counter_offsets` reste vide et `/metrics` donne les mêmes valeurs qu'avant.

Les séries à valeurs décimales (le coût et les sommes de durée, de premier token et de tok/s) sont des sommes en virgule flottante, et un recalcul peut arrondir différemment. Pour qu'elles ne baissent pas même au dernier chiffre, leur offset reçoit en plus une marge d'arrondi calculée pour chaque série, proportionnelle à la somme des valeurs absolues de ses lignes (et de son offset) et à leur nombre. Une série peut donc être à peine plus haute que le compte exact, avec une surestimation relative de l'ordre de 1e-9, jamais plus basse. Une série qui vaut 0 a une marge de 0 et reste à 0 ; les séries entières (comptages, tokens, octets) sont exactes.

Ils peuvent encore baisser, comme avant :

- par une **correction** de la lecture des messages, qui abaisse une valeur arrivée en direct : dans ce cas la lens suit la base, ainsi le dashboard et `/metrics` restent d'accord ;
- `opencode_lens_runs_total`, une fois, en mettant à jour une base plus ancienne que la v3 : sa migration retire les runs déduits à tort par la 0.3.0.

Prometheus lit une baisse comme une remise à zéro ; l'export OTLP en `delta` envoie 0 et repart de la nouvelle valeur, sans compter deux fois (voir [Export OTLP](#export-otlp)). Les séries d'IBM Bob n'ont pas d'offset : la rétention ne supprime pas les données de Bob.

### Utilisation des skills

`opencode_lens_skill_loads_total` et `opencode_lens_skill_preset_loads_total` comptent les chargements **terminés** : ceux en erreur restent dans la base et dans la page Skill, pas dans les compteurs. Ils sont monotones parce que les lignes de `skill_uses` ne sont jamais supprimées, pas même par la rétention. Les skills natives (`origin="native"`) y sont, même si la page Skill ne les montre pas. Les deux métriques et la table `skill_uses` restent du noyau : elles continuent de se remplir même avec le module Skill désactivé (la seule exception à « pas de métriques d'un module désactivé ») ; le désactiver retire la page et les routes `/api/skill*`, pas les compteurs.

- **Depuis quand on compte.** `skill`, `activated` et la ligne du preset de `lens-preset` ont tout l'historique d'OpenCode (la relecture après la migration vers la v5) ; les lignes par skill de `lens-preset` et `lens-prompt` partent du jour de la mise à jour, parce que c'est le processus MCP qui les écrit. C'est pourquoi `/api/skill-usage` donne `since` par canal et que la page écrit « comptages depuis … » et « Jamais utilisées depuis … ».
- **Le preset, c'est son id.** Les lignes sont sur l'id du preset : si un preset est supprimé et recréé avec un autre id, ou si `skill-presets.json` est modifié à la main, les anciennes lignes restent sur l'ancien id et ne bougent pas. La boîte de Lens ne change pas l'id d'un preset existant.
- Les livraisons faites pendant que la lens est éteinte sont perdues.

## Export OTLP

Avec `LENS_OTLP_ENDPOINT` la lens envoie les mêmes métriques et, si `LENS_OTLP_TRACES` n'est pas `0`, les traces à un collecteur OTLP/HTTP en JSON (`/v1/metrics`, `/v1/traces`) : OpenTelemetry Collector, Grafana Cloud, Datadog, Honeycomb, SigNoz. Configuration dans [configurazione.md](configurazione.md#export-otlp).

- **Métriques** : toutes les `LENS_OTLP_INTERVAL` secondes. Les compteurs sont `cumulative` par défaut ; avec `LENS_OTLP_TEMPORALITY=delta` (Datadog) on envoie la différence par rapport à l'export précédent. Les summaries ont `_sum` et `_count`.
- **Traces** : une trace par session racine. Chaque run est un span `opencode.run`, chaque step un span `opencode.llm` sous son run (attributs OpenInference et GenAI : modèle, provider, tokens, coût, finish), chaque tool un span `opencode.tool.<name>` sous son step. Depuis le schéma v4 les steps avec timings de streaming ont aussi `opencode.step.ttft_ms` et `opencode.step.output_tokens_per_second`, et les runs interrompus avec une raison connue `opencode.run.interrupt_reason`. Le span d'un run n'est envoyé qu'une fois, quand le run est synchronisé : en général l'événement d'interruption arrive d'abord et la raison y est, mais s'il arrive après l'envoi elle reste dans la base et dans les API et pas dans le span déjà exporté (il n'est pas renvoyé, parce que beaucoup de backends enregistreraient un second span avec le même id). Les runs d'un subagent sont sous l'appel `task`/`subagent` qui l'a lancé. Les ids de span dérivent de ceux d'OpenCode : un nouvel envoi après une erreur ne crée pas de doublons.
- Un run est envoyé quand la synchro l'a enregistré, c'est-à-dire après sa fin, avec tous ses steps et ses tools. Les runs sont pris dans l'ordre d'enregistrement : même un run synchronisé en retard part. Au premier démarrage la lens envoie la dernière heure, pas tout l'historique. Un step en dehors de tout run (session encore en cours) part avec le run quand celui-ci se ferme.
- En `delta` la base des différences n'est mise à jour qu'après un envoi accepté par le collecteur et est enregistrée dans la base : un envoi échoué est rattrapé au suivant, un redémarrage ne renvoie pas l'historique. La base est indexée par nom et étiquettes dans l'ordre canonique : une série que `/metrics` recrée à partir de `counter_offsets`, avec les étiquettes dans un autre ordre, ne semble pas nouvelle et n'est pas renvoyée en entier ; l'état enregistré par une version précédente est converti au chargement, donc la mise à jour ne renvoie rien. Si une série baisse (avec `counter_offsets` cela n'arrive que pour une correction du backfill) on envoie 0 et la base se réaligne sur la nouvelle valeur.
- Aucun prompt, réponse, input ou output de tools ne quitte la lens, comme pour la base. Les spans d'erreur ne portent que le type d'erreur, pas le message.
- L'état de l'export (dernier envoi, spans envoyés, dernière erreur) se trouve dans la page **Paramètres**.

Quand un compteur peut encore baisser, et ce qui reste des séries avec la rétention, est expliqué dans [Des compteurs qui ne baissent pas](#des-compteurs-qui-ne-baissent-pas).

Configuration du scrape :

```yaml
scrape_configs:
  - job_name: opencode-lens
    static_configs: [{ targets: ["127.0.0.1:4777"] }]
```

Pour qu'un Prometheus sur une autre machine puisse le lire il faut l'exposition à distance avec un token : voir [configurazione.md](configurazione.md#exposition-à-distance). Dans Prometheus le token va dans `authorization: { credentials: <token> }`.

Exemples PromQL :

```promql
sum by (model) (increase(opencode_lens_cost_usd_total[1d]))
sum by (model) (rate(opencode_lens_tokens_total{kind="output"}[5m]))
sum(rate(opencode_lens_step_duration_seconds_sum[1h])) / sum(rate(opencode_lens_step_duration_seconds_count[1h]))
```
