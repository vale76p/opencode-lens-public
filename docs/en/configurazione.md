# Configuration

🌐 [Italiano](../configurazione.md) · English · [Français](../fr/configurazione.md)

The lens has no configuration file: everything goes through environment variables. The values in use, with their origin (variable or default), the file paths and the database can be seen on the **Settings** page of the dashboard (`http://127.0.0.1:4777/#impostazioni`). With `opencode-lens service install` (or `install.sh` from a clone) the only one set in the LaunchAgent is `LENS_PORT`; the others are changed from the same page (see [Editing from the dashboard](#editing-from-the-dashboard)) or by hand in `~/Library/LaunchAgents/local.opencode-lens.plist` (`EnvironmentVariables` section), then reloading the service. Started by hand with `npm start`, the lens takes the variables from the shell and the page stays read-only. Running `opencode-lens service install` again (for example after a Node version change in a clone) preserves them: it rewrites the rest of the plist but keeps the `EnvironmentVariables` it finds, listing their names in the output, and changes `LENS_PORT` only with `--port 4800`; otherwise the port already in the plist stays. Updates (the new zip extracted over the app folder) do not touch the plist.

The values are checked at startup: if one is not valid the lens does not start and prints **all** the errors together (also `npm run check`). `LENS_*` variables the lens does not know, usually typos such as `LENS_PROT`, do not block startup: they end up as a warning in the log and on the Settings page.

The variables a module declares (today `LENS_SECURITY_DIRS` and `LENS_SECURITY_CONFIG_DIR`, of the Security module) are **module settings**: the lens knows them even with the module off, but reads them only while it is on, and they are edited from its card in **Settings › Modules**, never from the modules' files; the values are shown only on this computer and a secret is never shown. `--help` does not list them: they are in the module's manifest (see [moduli.md](moduli.md#a-modules-settings)).

## Editing from the dashboard

With the lens installed as a service (`opencode-lens service install`, macOS LaunchAgent) the **Environment variables** table of the Settings page is a form: each variable has the value written in the plist next to the one in use. *Save and restart*:

1. checks the values with the same rules as startup and, if something is wrong, shows **all** the errors without touching anything;
2. if port or interface change, verifies that the new port is free;
3. rewrites only the plist's `EnvironmentVariables` (on a copy checked with `plutil -lint`, then replaced);
4. reloads the service (`launchctl bootout` + `bootstrap`, because launchd reads the environment only at load); the page waits for the lens to restart, or goes to the new address if the port changed.

An empty field removes the variable (the default returns). Secrets (`LENS_TOKEN`, `OPENCODE_SERVER_PASSWORD`, `LENS_OTLP_HEADERS`) are never shown: an empty field leaves them as they are, *remove* deletes them. Unknown `LENS_*` variables found in the plist can be removed with a button; so can `LENS_BOB`, which the lens no longer reads (“Remove” button). If the plist was edited by hand and not yet reloaded, the page says so and a save with no changes applies it.

Changes are accepted only from this computer (connection from `127.0.0.1` or `::1`), even when the dashboard is reachable from the network, and with `LENS_TOKEN` the token is required as for the rest. If you change `LENS_TOKEN` you will have to reopen the dashboard with the new `?token=`. If the lens does not restart (for example the port got taken in the meantime), the reason is in the log.

To restart the lens without changing any variable (for example after adding a module by hand to the modules folder) there is the **Service** box at the bottom of Settings › General, with the *Restart the lens* button: it asks for confirmation, reloads the service like *Save and restart* but without touching the plist, waits for the lens to come back and stays in the same section. The same rules as for the other changes apply (only from this computer, only with the lens installed as a service): otherwise the button is disabled and says why. It is disabled also when the plist cannot be read (reloading it would leave the lens down) or has variables edited by hand and not applied yet: reloading it would apply them without the checks of *Save and restart*, which is the way to apply them. Behind it is `POST /api/restart` (see [metrics](metriche.md)).

Example, to follow a standalone server:

```bash
OPENCODE_SERVER_URL=http://127.0.0.1:4096 OPENCODE_SERVER_PASSWORD=… npm start
```

## Language and format

The dashboard exists in Italian, English and French. The two choices are independent and are made on the **Settings** page, **Language and format** card:

- **Language** (`LENS_LANG`): `Automatic` follows the browser's first language among Italian, English and French; if none is supported, the interface is in English. A forced language applies to every browser that opens the dashboard.
- **Format** (`LENS_LOCALE`): dates, times and numbers. `Automatic` uses the browser's first format with a region, if it is among those offered (`it-IT`, `en-US`, `en-GB`, `fr-FR`), otherwise the usual one of the chosen language (`it-IT`, `en-US`, `fr-FR`). You can have the dashboard in English with Italian-style dates and times, or the other way around.

Saving reloads the page in the new language. The choices live in the plist like the other variables, not in the browser. The browser sends the chosen language to the server (`X-Lens-Lang`, `X-Lens-Locale`) and the texts the server writes for people (errors, descriptions, status) follow it too; without these headers they are in Italian. The log, the `HELP` lines of `/metrics` and the output of the MCP tool stay in Italian.

Some technical terms are not translated in any of the three languages (token, prompt, cache, budget, step, tool, retry, agent, provider, widget, dashboard…). How to add or fix a translation: [traduzioni.md](traduzioni.md).

## Budget

The “Today” bar at the top of the dashboard compares the current day with the budgets you set. Without budgets it shows only the usage. For example, 5 million tokens and 300 steps a day:

```bash
LENS_LIMIT_TOKENS=5000000 LENS_LIMIT_STEPS=300 npm start
```

With the LaunchAgent add them to the plist's `EnvironmentVariables` and reload the service; running `opencode-lens service install` again does not delete them. The same values are in `/metrics` (`opencode_lens_daily_limit`) to build an alert on them.

Week and month have budgets of their own, by calendar in local time (week from Monday 00:00, month from day 1). The OpenCode Lens Monitor app uses them for the percentage in the bar, the cards and the widgets, reading them from `/api/budget`. Example, 50 million tokens a week and 200 million a month:

```bash
LENS_LIMIT_TOKENS_WEEKLY=50000000 LENS_LIMIT_TOKENS_MONTHLY=200000000 npm start
```

For each period and metric `/api/budget` reports used, limit, ratio, linear projection at the end of the period (only after 1 hour for the day, also on the days of the clock change, and after 1/24 of the period for week and month: 7 hours for the week) and the pace: `none` without a limit, `under`, `over` if the projection exceeds the limit, `exceeded` if the limit is already exceeded.

### Budget per model

When each model has its own quota, for example a company server with 4 local models and 100 million tokens a day each, set the budgets from the **Settings** page, **“Budget per model”** card.

The models come from the **OpenCode global configuration**: the files `opencode.jsonc`, `opencode.json` and `config.json` in `~/.config/opencode` (or `$XDG_CONFIG_HOME/opencode`), section `providers` → `<provider>` → `models` (also the `provider` of the previous schema). Each model becomes `provider/model`, the name of the dashboard's per-model table; its `name`, if there is one, appears next to it. For example:

```jsonc
{
  "providers": {
    "company": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": { "baseURL": "http://llm.company.lan/v1" },
      "models": {
        "qwen3-coder": { "name": "Qwen3 Coder" },
        "llama-4": { "name": "Llama 4" }
      }
    }
  }
}
```

- Next to each model write the **tokens per day**: an integer, or `100M`, `1.5M`, `500k`, `2G`. Empty = no budget. “Save and restart” writes `LENS_MODEL_LIMITS` into the LaunchAgent and restarts the lens; the button also saves the changes of the other Settings fields together.
- `LENS_MODEL_LIMITS` is no longer edited by hand: in the variables table it is read-only, and the page refuses to change it from there.
- **History**: a model that disappears or changes name in the OpenCode configuration no longer counts (it disappears from the widget and the gauges), but its budget stays at the bottom of the card, read-only, as “no longer in the configuration”. If the model comes back, it finds its budget again.
- The configuration is reread when it changes, without restarting the lens.
- **Configuration not available** (no file, invalid JSON, unreadable file): the card says so with the path and the error, all budgets stay active and cannot be changed until the configuration is readable again.
- All variants of a model (`#high` and the like) consume the same budget.
- A model the lens has never seen is flagged in the widget and in the gauge (“never seen”).
- The model's steps count. OpenCode's internal tasks (titles, compaction) have no model in the database and stay out, while the server counts them: keep some margin.
- Without the LaunchAgent (lens started by hand or dashboard opened from another computer) the card is read-only; in that case `LENS_MODEL_LIMITS` is still passed as an environment variable, in the format `provider/model=tokens,…`.

They are seen in the “Per model today” widget and in the “Daily budget of a model” gauges (see [dashboard.md](dashboard.md)), and in `/api/budget` under `periods.day.models`.

### Price list

The “Price list” card (Settings › Budget) is the per-model price list: modules use it to estimate a cost. It does not change the cost the lens shows, which stays the one OpenCode computes.

- The rows are the models in OpenCode's configuration, those used in steps in the last 90 days and those already priced, with their tokens of the last 30 days.
- For each model write the dollars per million tokens: **input** and **output**, and optionally **cache read** and **cache write**. If you leave them out, cache read is 10% of input and cache write is the same as input. Reasoning is billed like output.
- “Save and restart” writes `LENS_MODEL_PRICES` into the LaunchAgent, in the format `provider/model=input:output[:cacheRead[:cacheWrite]],…` (for example `anthropic/claude-sonnet=3:15`). Like `LENS_MODEL_LIMITS`, it is not edited by hand. Keys with spaces, `?` or `#` are rejected.
- Variants of a model (`provider/model#variant`) get the base model's price. A model without a price stays without one: the lens does not invent it.
- The estimate counts only steps, like the spent cost, without OpenCode's internal tasks.

### Reset hour

The budget day starts at midnight. If the server that applies the quota resets at another hour, set it in `LENS_RESET_HOUR`:

```bash
LENS_RESET_HOUR=2     # from 02:00 local to 02:00 the next day
LENS_RESET_HOUR=0Z    # from UTC midnight: 02:00 in Italy in summer, 01:00 in winter
```

With the `Z` the hour stays right even when daylight saving changes. It applies to all daily budgets (`LENS_LIMIT_*` and `LENS_MODEL_LIMITS`), to “Today”, to the day of “Today”, to the day's gauges, to `/api/today` and to `opencode_lens_today` in `/metrics` and OTLP. Week and month stay by calendar (Monday 00:00 and day 1 00:00, local time), like the per-day charts and the last year's calendar: with a reset hour other than 0 the sum of the budget days may not match the week exactly.

## Detail retention

By default the lens keeps everything forever. With `LENS_RETENTION_DAYS`, an integer between 400 and 36500, it deletes the OpenCode steps and tool calls older than that number of days, counted from local midnight; unset, or empty, the retention is off. It can also be set from **Settings › General › Keep details**. The minimum of 400 days keeps exact every fixed window of the dashboard, none of which goes beyond the calendar's 370 days: days, hours, rhythm, day, week and month budgets.

- **What it deletes**: only OpenCode's `steps` and `tools` rows.
- **What stays**: sessions, prompts, runs, internal tasks, signals (retries, compactions, failed executions), permissions, skill usage and all IBM Bob data.
- **What stays in the numbers**: before deleting a day the lens sums its steps and tools into a daily rollup (`daily_steps` by session, model and agent; `daily_tools` by tool name) and saves in `counter_offsets` what they counted in `/metrics` (see [Counters that do not go down](metriche.md#counters-that-do-not-go-down)). So the summary totals of “All”, the counters of `/metrics` and of the OTLP export and the check *Σ steps + Σ internal tasks = OpenCode's totals* (also `npm run verify`) do not change. A resync does not put the pruned rows back: the lens does not rewrite steps and tools older than the limit.
- **When**: 60 seconds after startup and then every 6 hours, one day per transaction; between one day and the next the collector and the dashboard keep working. In the log: `retention: N giorni potati (… step, … tool) prima del …`.
- **The file does not shrink**: the lens does not run `VACUUM`. The freed space is reused for new rows.

Limits:

- In “All” charts, breakdowns (by model, agent, folder…), sessions, prompts, session detail, latency and speed show only the rows kept; only the summary totals (`/api/summary`: steps, failed steps, cost, tokens, distinct sessions and models, tool calls and errors) include the pruned days.
- A prompt (run) of a pruned day stays, with outcome and duration, but without steps, tokens and cost; a retry of those days stays, but without the model.
- In a period chosen by hand a pruned day counts in the totals only if the period contains its midnight, so two adjacent periods do not count it twice. The exception is the period that contains the start of the oldest pruned row, like “All”: it also counts the day it starts in.
- IBM Bob is not pruned: its tables grow as before.
- Settings and `/api/status` do not show the state of the retention: there is only the log line.

## OTLP export

To send metrics and traces to an OpenTelemetry collector, to Grafana Cloud or to Datadog:

```bash
# Local OpenTelemetry Collector
LENS_OTLP_ENDPOINT=http://127.0.0.1:4318 npm start

# Grafana Cloud
LENS_OTLP_ENDPOINT=https://otlp-gateway-prod-eu-west-2.grafana.net/otlp \
LENS_OTLP_HEADERS="Authorization=Basic <base64 instance:token>" npm start

# Datadog: delta only
LENS_OTLP_ENDPOINT=https://otlp.datadoghq.eu LENS_OTLP_HEADERS="dd-api-key=<key>" LENS_OTLP_TEMPORALITY=delta npm start
```

On the Settings page and in the log the endpoint appears without credentials (`user:password@` and query string hidden). The lens uses OTLP/HTTP with JSON encoding, without an SDK: the endpoint must accept it (the Collector and the services mentioned accept it on `/v1/metrics` and `/v1/traces`). `LENS_OTLP_HEADERS` usually holds a secret: keep it out of version control. What is sent: [metriche.md](metriche.md#otlp-export).

## Prices for local models

The cost is computed by OpenCode, not by the lens, from the prices per million tokens declared in the model's config. For local models it is 0, unless you declare a price in OpenCode's config:

```jsonc
{
  "providers": {
    "lmstudio-local": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": { "baseURL": "http://127.0.0.1:1234/v1" },
      "models": {
        "qwen3.5-9b": { "cost": { "input": 0.1, "output": 0.4, "cache": { "read": 0.01, "write": 0 } } }
      }
    }
  }
}
```

## MCP server for OpenCode

`opencode-lens mcp` is an [MCP](https://modelcontextprotocol.io) server on stdio: the models working in OpenCode V2 can ask Lens for budget, errors, usage, sessions and what the DLP guards did, and receive the skills of a preset you choose (see [Prompts](#prompts)). It talks only to the lens's HTTP API on `127.0.0.1`, does not open the database and changes neither the models nor OpenCode's configuration. It is not read-only: when it delivers a preset (`prompts/get` or the `preset` tool) it reports it to the lens with `POST /api/skill-loads` (preset id and delivered skills, never texts), to count usage. With a lens that is off or old the delivery still reaches the model and the count is silently lost. The `preset` tool, the `/lens:<id>` commands and the delivery count exist only with the **Skill** module on (see [moduli.md](moduli.md#skill)); off, `/api/skill-loads` answers 404 and the delivery is not counted.

### Installation

The simplest way is the **MCP server** section of Settings in the dashboard. It has three tabs, all already filled in with this installation's paths and with a “Copy” button:

- the command to run;
- the same server as a block for `opencode.jsonc`;
- a prompt to paste into OpenCode so that the model adds the server. The prompt edits only `mcp.servers.lens` and touches neither agents nor permissions.

The same section shows whether the server is running. The state is read from OpenCode (`GET /api/mcp`, for the service's default folder) and from the global configuration: Lens recognizes the server by the name `lens` and never writes to OpenCode's configuration. To turn it on or off you use OpenCode (`"disabled": true`, or removing the `lens_*` permission from the agents), then `opencode2 reload`.

The “Running MCP” row says which version of the MCP last called the lens and when. When it is not the lens's one (typical after an update: the MCP is a child process of OpenCode and stays the old one), the “Restart OpenCode” notice appears: see [The MCP server: restart OpenCode](aggiornamento.md#the-mcp-server-restart-opencode).

From the terminal:

```bash
opencode-lens mcp install
```

The command prints the line to run, with absolute paths: the `node` and the `main.js` of the LaunchAgent or, without a service, those of the process that launched it. For example:

```bash
opencode2 mcp add --global lens -- /opt/homebrew/opt/node/bin/node /Users/you/Applications/opencode-lens/src/main.js mcp
```

The line adds `mcp.servers.lens` to OpenCode's global configuration. OpenCode starts the command without a shell, so no `~`. A lens update does not require repeating it, because the path stays the same. It has to be redone only if the app changes folder or if the plist's Node changes.

Port and token come from the LaunchAgent's `EnvironmentVariables`, so the token does not end up in clear in `opencode.jsonc`. In the MCP server's environment (`--env` of `opencode2 mcp add`) `LENS_PORT`, `LENS_TOKEN` and `LENS_RESET_HOUR` prevail over the plist. Without a plist the defaults apply (`4777`, no token). The MCP always connects to `127.0.0.1`: if the lens listens only on a network address (`LENS_HOST` other than `0.0.0.0` and loopback), the MCP does not reach it.

### Tools

OpenCode shows them with the server prefix: `lens_budget`, `lens_errors`, `lens_usage`, `lens_sessions`, `lens_module_guide`, `lens_module_check`, `lens_security` (only with the Security module on) and `lens_preset` (only with the Skill module on). Permissions per agent are given on these actions. They all read from the lens; the only write is the count of `preset` deliveries (see above), which changes nothing of what the model receives. `module_check` makes a `POST /api/modules/check`, but it is only a query: the lens judges the module without activating it or changing anything. To judge it, though, it runs the module's code in the lens process: that is why `module_check` is not declared read-only.

After the lens update that brings them, `lens_module_guide` and `lens_module_check` appear in OpenCode only once it is restarted (see [The MCP server: restart OpenCode](aggiornamento.md#the-mcp-server-restart-opencode)).

| Tool | Arguments | Typical questions |
|---|---|---|
| `budget` | – | “how much do I have left today on Opus?”, “at this pace will I overshoot the week?” |
| `errors` | `since` (`1h`, `6h`, `24h`, `7d`; default `24h`), `session` (`current` or an id), `scope` (`project` or `all`), `limit` (1–30) | “why have requests been failing since this morning?”, “what happened to this session?” |
| `usage` | `range` (`today`, `yesterday`, `7d`, `30d`, `month`; default `7d`), `by` (`model`, `provider`, `agent`, `tool`, `day`), `compare` | “compare this week with last week”, “which agent costs the most?” |
| `sessions` | `range`, `sort` (`cost`, `tokens`, `errors`, `recent`), `limit` (1–20), `scope`, `id` (`current` or an id) | “the most expensive sessions of the month”, “detail of this session” |
| `module_guide` | `section` (optional: the title, or part of the title, of a section of the guide) | “write a Lens module that shows the files of a folder”, “what do I need to know about a module's widgets?” |
| `module_check` | `id` (the module, i.e. the name of its folder: lowercase letters, digits and hyphens) | “check the mio-modulo module” |
| `security` | `guard` (the name), `session` (`current` or an id), `scope` (`project` or `all`), `since` (`1h`, `6h`, `24h`, `7d`; default `24h`), `outcome` (`blocked`, `allowed`, `all`), `limit` (1–30) | “what did the DLP guards block today?”, “is the Context7 guard working?” |
| `preset` | `name` (the id or the name of a preset; the id is the one in `/lens:<id>`), `skill` (the id of a library skill) | “which skill presets do I have in Lens?”, “use the angular-security preset for this job” |

How they work:
- **Calling session.** It comes from `_meta["ai.opencode/sessionID"]`, which OpenCode adds to every call. `errors` and `sessions` stay by default within the project (the folder) of that session; with `scope: "all"` you see all of them.
- **Errors.** They are grouped by source (step, tool, retry, failed execution), model, type and HTTP status. Retries and failed executions exist only since Lens sees them live: the answer says since when it counts them. If an error interrupted the current session, the question is asked in the next turn.
- **Comparisons.** `compare` compares with the immediately preceding period, at the same elapsed duration (today up to 10:40 against yesterday up to 10:40). The MCP computes the differences, the model just reports them. The days are the budget days, as in the dashboard (`LENS_RESET_HOUR`).
- **Budget.** These are the limits you chose (`LENS_LIMIT_*`, `LENS_MODEL_LIMITS`), not the provider's quotas: Lens does not see how much is left at the provider. With a session in progress there is also the context fill.
- **Model switching.** The MCP changes neither model nor configuration. Its instructions tell the model that the automatic switch to a backup model, when the provider runs out of quota or does not answer, is done by the [lens-guard plugin](#plugin-lens-guard-switching-model-when-the-provider-does-not-answer), and that Lens budgets do not make it switch model for now.
- **Security.** Only with the Security module on. Says what the DLP guards found in OpenCode's folders (today Context7 Guard) let through or blocked, with the categories detected, the guard's health and its global policy; without `guard` and with several guards it gives the summary. Never the findings text nor the previews, and the policy's lists only as “N entries”. A tool that failed with “GUARD — invio bloccato” is a DLP block, not a failure: ask here. Details in [sicurezza.md](sicurezza.md#mcp-tool-security).
- **Modules and restarting OpenCode.** A module's tools (today `security` and Skill's `preset`) and the lines they add to the server's instructions exist only while the module is on. The MCP notices within 30 seconds and tells OpenCode with `notifications/tools/list_changed`, but OpenCode (verified with 2.0.26) rereads neither the tools nor the instructions: after turning a module with tools on or off, **restart OpenCode**. Until then it sees the old list, and a tool of an off module answers “Il modulo <Name> è spento in Lens: attivalo da Impostazioni › Moduli.”. See [moduli.md](moduli.md#a-modules-mcp-tools).
- **Presets.** With no arguments `preset` gives the up-to-date list of presets (id, name, brief, skills). With `name` it gives the skills of that preset; with `skill` (and `name` omitted) a single library skill, useful when the text of a preset was shortened (if both are given, `skill` wins); a body over 48 KiB or 1900 lines is cut at a whole line, with a note that points to `SKILL.md`. `name` is the preset id or name: the id counts first, then the display name (case-insensitive, without spaces at the edges; if several presets have the same name the id is asked for). A `name` that does not exist is an error in Italian that lists the valid ids (at most 30) and points to the list. Every successful delivery is counted (see [Skill usage](metriche.md#skill-usage)). It is not an observation of OpenCode: it is your own instructions, see [Prompts](#prompts) and [What reaches the model](#what-reaches-the-model). Only with the Skill module on: OpenCode does not reread the tool list, so the tool appears or disappears only after OpenCode is restarted; with Skill off it answers “Il modulo Skill è spento in Lens: attivalo da Impostazioni › Moduli.”
- **Writing a module.** `module_guide` and `module_check` are core tools, always there (no module turns them on), so that a model can write a module in the user's modules folder (see [moduli.md](moduli.md)). `module_guide` gives the app's guide (`docs/moduli-custom.md`) or, with `section`, only the section whose title contains that text (case ignored; with no match it lists the titles), plus the values of this installation read from `GET /api/modules/authoring`: the user's modules folder, the lens version, and the ids, `LENS_…` variables, `/api` paths, MCP tools and widget types already taken, and the widget limits. If the guide is missing it says so and still gives the values; if the lens does not answer it gives the guide and says the values are missing. `module_check` asks `POST /api/modules/check` to judge the module in the user's folder as at startup, without activating it (it does run the top-level code of `module.js`, `tables.js` and `server/index.js`, and `configure()`, in the lens process): it answers “OK” or the errors and warnings, one per line (with `isError` if there are errors), even for a new module the lens has not discovered yet; the model fixes and calls again until it is “OK”. A module cannot declare tools with these names. As with other new tools, they show up in OpenCode after a restart. They work only from this computer: the lens's two paths refuse anyone who is not local.
- **Freshness.** Every answer ends with a line on the collector's state, on the last event seen and on the drift of OpenCode's API.
- **MCP errors.** If Lens is off or the token is wrong, the tool answers with an error in Italian that says what to check (`opencode-lens service status`, `LENS_TOKEN`).

It supports MCP revisions 2025-11-25 (`initialize`) and 2026-07-28 (`server/discover`). OpenCode 2.0.26 uses the first.

### Prompts

A **preset** groups skills of the Lens library (the **Skill** page, see [dashboard.md](dashboard.md#skill)) under an id you choose, a name and a brief. The MCP offers them in three ways: They are a feature of the Skill module: the commands, the tool and the instructions below exist only with the module on (Settings › Modules).

- **Prompts.** One per preset: `name` is the preset id, `title` the name, `description` the brief, on one line and without «» quotes. In OpenCode they become the `/lens:<id>` commands: writing `/lens:api-docs` followed by the task hands the preset's skills to the model. `prompts/get` answers with a message that starts with «Usa queste skill per il compito che segue.» (“Use these skills for the task that follows.”) and goes on with the preset's text (see [What reaches the model](#what-reaches-the-model)). The commands follow `notifications/prompts/list_changed`: turning Skill on or off makes them appear or disappear in OpenCode without a restart (the `preset` tool, instead, changes only after OpenCode is restarted).
- **Tool.** `preset` (see [Tools](#tools)), for when the model decides: “use the angular-security preset for this job”.
- **Instructions.** At `initialize` the list of presets (id, name, brief and skill ids) is appended to the server's instructions, so the model knows they exist and when to use them: if the task matches the brief of a preset, it must ask for it with `preset` before starting. The list is capped at about 3000 characters: briefs cut to 160, at most 300 characters of skill ids per preset, and if the presets do not all fit a final line says how many are missing (“… e altri N preset: chiedi preset senza argomenti per l'elenco completo”). A skill that is gone from the library is marked “(assente)”. The instructions are read once per connection, with 3 seconds of time: with Lens off or slow they stay the usual ones, without a list. The up-to-date, complete list is given by `preset` with no arguments. The list goes at the end of the instructions, after a blank line, and the Skill module writes it; its fixed lines (presets and deliveries) follow those of the core's tools.

If the presets change (a new one or one removed, or a different name, brief or skills of one), the MCP sees it within 30 seconds, because it checks every 30, and sends `notifications/prompts/list_changed`: the client reads `prompts/list` again. The starting point is what the client actually received with its last `prompts/list` (an empty list if it had failed): a Lens that comes back after that failure is announced at once, and the same change is not announced at every check. Until the client has asked anything, the first reading after startup only sets the starting point. Changing the text of a skill is not a change of the presets: every request reads the library again, so it arrives with the next request.

Errors of `prompts/get`: without `name`, or with a preset that does not exist, it is `-32602` (invalid request); with Lens off, a wrong token or an invalid configuration it is `-32603` (internal error). With Lens off, a wrong token or an invalid configuration `prompts/list` answers with an empty list and writes the reason to stderr, once per reason. With the Skill module off, in error or unconfigured `prompts/get` answers with a text saying so (off, in error, to be configured), not with a generic error.

### What reaches the model

Lens does not save prompts or outputs, but some fields may contain pieces of them:
- provider error messages may quote the request;
- tool errors are tool output (stderr, web pages);
- session titles summarize the prompts.

Sending them to a model, even from one session to another, is a data exit and a possible prompt injection channel. That is why the MCP:
- by default sends only error class, HTTP status and counts;
- sends the error text only for one session (`session`, or `sessions` with `id`), or everywhere with `LENS_MCP_ERROR_TEXT=1`:

  ```bash
  opencode2 mcp add --global --env LENS_MCP_ERROR_TEXT=1 lens -- <node> <main.js> mcp
  ```
- from `security` never pass the findings text (`detail`) nor the arguments' previews, and policy values that look like keys are masked; the calls' objects, tool names and categories do, cleaned like the other texts;
- cleans texts and titles of newlines, control characters, bidi characters and invisible characters (zero width, variation selectors, Hangul fillers), cuts them to 160 characters (80 for titles) and puts them between «».

The `preset` (tool and prompt) is the deliberate exception: it sends **text**, that of your skills, because that is its purpose. It is not OpenCode data but your own configuration, which you imported and chose in the Skill page, and that is why the text arrives as it is, without the cut to 160 characters: the MCP cleans only control characters (newlines and tabs stay, the others become a space) and removes invisible ones (zero width) and bidi ones; variation selectors stay, because emoji such as ✔️ use them. The name and brief of the preset, in the first line, are instead still cleaned to one line and put between «», followed by the list of its skills. For each skill of the preset it sends:

```
Preset «Documentare le API» (api-docs): «Mappa e documenta le API HTTP di un progetto, poi verifica a runtime.» · skill: api-explore, sparita (assente)
<skill_content name="api-explore">
# API Explore
…
Cartella base di questa skill: /Users/…/Application Support/opencode-lens/skills/api-explore/2
I percorsi relativi (scripts/, references/…) partono da lì.
<skill_files>
<file>/Users/…/skills/api-explore/2/references/discovery-heuristics.md</file>
</skill_files>
</skill_content>
Skill «sparita» assente dalla libreria di Lens.
```

- the body of `SKILL.md`, without the frontmatter, inside `<skill_content name="…">`;
- the absolute **base folder** of the version in use (“Cartella base di questa skill: …”): the relative paths in the text (`scripts/`, `references/`…) start from there, and the model reads them with its own tools;
- the skill's description, whole up to 1024 characters (“Descrizione: …”);
- the absolute paths of the skill's other files, in `<skill_files>` (the first 10), as they are on disk: spaces and quotes stay, and a path with control, bidi or invisible characters is not altered but left out, with the note “(N file con nomi non sicuri omessi)”;
- if a skill of the preset is no longer in the library, a line that says so (“Skill «sparita» assente dalla libreria di Lens.”);
- if a skill cannot be read (Lens answers with an error other than “not found”), a line “Skill «id» non leggibile ora: …” in its place: the others arrive all the same.

The text of all the skills in one answer has **three caps, which hold together**: 40,000 characters, 48 KiB of UTF-8 bytes and 1900 lines. OpenCode cuts a tool result at 50 KiB or 2000 lines, and non-Latin text weighs more bytes than characters. A skill that does not fit in the total arrives without its body, with its folder and its files and a note to read `SKILL.md` with the `read` tool or to ask `preset` with `skill="<id>"`; a smaller one after it may still fit, and if not even that form fits a single line arrives; when not even the lines fit, the last skills are gathered into one counted line (“… e altre N skill non incluse: …”). With `skill` there is no 40,000-character cap but the 48 KiB and 1900 lines remain: a body that passes them is cut at the last whole line that fits, with a note that points to `SKILL.md` in the base folder, where the model reads the rest.

Lens never runs a skill or its scripts: the model reads or runs them, with the tools and permissions it has in OpenCode.

The files are in `~/Library/Application Support/opencode-lens/skills/`, outside the project OpenCode is working on. If `read` or `bash` ask for confirmation for the files of that folder, you can try adding to `permissions` in OpenCode's configuration a rule that allows `read` on that folder (Lens never writes to OpenCode's configuration). It is a possibility, not yet verified.

## Remote exposure

To have it read by a Prometheus on another machine three variables are needed. Without a token the lens refuses to start on a non-local interface.

```bash
LENS_HOST=0.0.0.0 LENS_TOKEN="$(openssl rand -hex 24)" LENS_ALLOWED_HOSTS="macbook.local:4777" npm start
```

The token can be passed in three ways:

- `Authorization: Bearer <token>` header (Prometheus: `authorization: { credentials: <token> }`);
- `?token=<token>` once in the browser: the lens answers with a redirect that removes the token from the URL and sets the `lens_token` cookie (`HttpOnly`, `SameSite=Strict`);
- `lens_token` cookie.

`LENS_ALLOWED_HOSTS` must contain the name the lens is reached by, port included: requests with another `Host` receive 403.

### Behind a reverse proxy

If the lens is published by a reverse proxy on the same Mac (nginx, Caddy, `ngrok`, `cloudflared`, Tailscale Serve or Funnel), for the lens every request comes from `127.0.0.1`, including those coming from the network. If the proxy also rewrites the `Host`, the check on the `Host` is no longer enough: in this case **always set `LENS_TOKEN`**, even with `LENS_HOST=127.0.0.1`, otherwise anyone who reaches the proxy reads all the data.

Changes (settings, dashboard layout, skills and presets, update) never go through the proxy: `POST` requests with proxy headers (`Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Real-IP`, `Via`, `CF-Connecting-IP`, `Tailscale-*`) receive 403, even with the right token. To change them open the dashboard directly from this Mac (`http://127.0.0.1:4777`). For clients behind a proxy `GET /api/settings` shows `LENS_OTLP_ENDPOINT` obscured, like `/api/about`. The check applies only to proxies that add at least one of these headers: verify that yours does.

## Plugin lens-guard: switching model when the provider does not answer

`extras/opencode/lens-guard.v2.ts` is a plugin for OpenCode 2.x. When the provider cannot answer, the turn continues on a backup model: there is no need to resend the prompt. It works inside OpenCode and does not need the lens: the lens sees only the result, that is the step counted on the backup model.

The plugin switches model in three cases:

- **quota exhausted**: 429 with `insufficient_quota`, `billing` or similar, errors that OpenCode does not retry;
- **rate limit with a long `Retry-After`**: OpenCode would wait at least `minRetryDelayMs` (60 seconds by default, up to 15 minutes) before retrying;
- **provider unreachable**: connection refused, server name not resolved, no network. A connection that drops halfway through an answer does not count: OpenCode retries it on the same model.

Other errors (authentication, content policy, short rate limits, provider internal errors) are left to OpenCode, which handles them as usual. A short rate limit stays such even when the provider writes “quota” in the message, as Gemini does for per-minute limits.

### Installation

With the lens installed from the zip, the plugin is in `~/Applications/opencode-lens/extras/opencode/`:

```bash
cp ~/Applications/opencode-lens/extras/opencode/lens-guard.v2.ts ~/.config/opencode/plugins/
```

```bash
cp ~/Applications/opencode-lens/extras/opencode/lens-guard.example.json ~/.config/opencode/lens-guard.json
```

Edit `lens-guard.json` and restart OpenCode. Lens updates do not touch the copy in `plugins/`: after an update repeat the first command if you want the new version. Uninstalling the lens also leaves it in place.

### Configuration

```json
{
  "fallback": {
    "anthropic/claude-opus-4-1": ["anthropic/claude-sonnet-4-5", "openai/gpt-5"]
  },
  "minRetryDelayMs": 60000
}
```

- `fallback`: for each model, the backup chain in order. Models are written `provider/model`, as in `opencode2 models`; everything after the first `/` is the model id (`openrouter/anthropic/claude-sonnet`).
- `minRetryDelayMs`: from which wait in milliseconds a rate limit makes it switch model. Default `60000`.

The file is **plain JSON**: no comments or trailing commas. A file with comments or invalid, or a `fallback` that is not an object, turns the plugin off without errors and OpenCode continues as if it were not there. Individual invalid entries are discarded: one without `/`, a model that points to itself, duplicates.

The file is at `${XDG_CONFIG_HOME:-~/.config}/opencode/lens-guard.json`. `LENS_GUARD_CONFIG=/path/file.json` points to another one, `LENS_GUARD=off` turns the plugin off. They are OpenCode environment variables, not the lens's.

### How it behaves

- The switch happens inside the turn: OpenCode retries the same step on the backup model, without waiting. In the TUI the line “Switched model from … to …” appears, the only notice: the plugin adds no messages to the conversation, which would cost an extra step.
- In the lens the retried step appears only once, on the backup model, with 2 attempts. The first attempt's error stays in the retries recorded live.
- The session **stays** on the backup model in the following turns too. The plugin does not go back by itself: to return to the previous model choose it again in OpenCode.
- Each chain is walked **only once per turn** and no model is retried in the same turn. The chain is that of the first model that fails: with `A → [B]` and `B → [A]`, if both fail there is a single switch, then the error is left to OpenCode. At the next prompt it starts over.
- Changing provider mid-conversation loses the previous provider's prompt cache: the first step on the backup model pays the whole context again.

## IBM Bob

The **IBM Bob** module, turned on from Settings › Modules (see [moduli.md](moduli.md)), reads **IBM Bob** tasks (Bob IDE 2.x and Bob Shell 2.x), which keep them in the same SQLite database, `~/.bob/db/bob.db`. Bob has no API or event stream: the lens opens the file read-only every `LENS_BOB_INTERVAL` seconds, re-reads the tasks that moved and stores them in tables of its own (`bob_tasks`, `bob_requests`, `bob_tools`), created by the module and never pruned. It does not touch Bob's configuration and never stores titles, prompts, message text, tool arguments or outputs: only folder, mode, status, times, cost, tokens and tool names (Bob does not record the model it picks). Bob deletes tasks after 30 days; the lens keeps them.

OpenCode's numbers do not change: Bob's tables are separate, `/api/summary` is the one it always was and OpenCode's `/metrics` series are identical. Bob appears in the dashboard only where you ask, with the **OpenCode · + Bob · Bob only** selector (see [dashboard.md](dashboard.md#ibm-bob)); Bobcoins become dollars with `LENS_BOB_COIN_USD`.

The four `LENS_BOB_*` variables in the table are **settings of the module**: they are changed from its card in Settings › Modules (`LENS_BOB_INTERVAL` between 5 and 3600, `LENS_BOB_COINS_MONTHLY` at least 1) and apply only while the module is on. **`LENS_BOB` is no longer needed**: whoever used it finds Bob off after the upgrade, because the lens ignores it (one line in the log), and a notice on every page says Bob is no longer read until you turn it back on from Settings › Modules and that what Bob deletes in the meantime is lost. “Remove”, in Settings, takes the variable out of the LaunchAgent. The “+ Bob” or “Bob only” choice of the selector starts again from “OpenCode”. The `bob_*` tables stay in the database even with the module off: rows and tables are never deleted (see [disinstallazione.md](disinstallazione.md)).

IBM does not document bob.db's schema. If it changes (an expected table or column is missing) reading Bob is paused and the dashboard says so; OpenCode goes on as before. `node modules/bob/scripts/bob-probe.mjs` shows the schema of this computer's bob.db and the shape of its fields, without any text. `node modules/bob/scripts/bob-probe.mjs --account` looks instead for where Bob keeps your account's consumption (Bobcoins used, plan, renewal): Bob IDE's saved state, `~/.bob` and the code of Bob IDE and Bob Shell; here too only shapes and names, never text nor tokens. `--checks` verifies what the lens takes for granted: it estimates how many Bobcoins a million tokens of each kind cost (fresh input, cache read, cache write, output, with a regression on the calls: IBM does not publish the conversion), checks that `input` includes the cache, that a task's cost is the sum of its calls and whether it includes its subagents, counts hidden prompts and the days covered, and measures the messages Bob writes late: how many it writes after a newer one of the same task, the longest delay and how many go beyond the 60 seconds the lens reads again at every pass (it also counts the assistant messages without `_meta.spend`). The three probes also run from the IBM Bob panel in **Settings › Modules**, from this computer only and only with the module on: the result can be copied or downloaded as a text file.

## Security and privacy

- It listens only on `127.0.0.1` by default. It accepts only requests with a local `Host`, as protection from DNS rebinding. Only GET (and HEAD), restrictive CSP, no CORS. The only exceptions are `POST /api/settings` (editing variables), `POST /api/dashboard` (dashboard layout), `POST /api/presets` (its presets), `POST /api/skills` and `POST /api/skills/<id>` (skill library), `POST /api/skill-presets` (their presets), `POST /api/vibe-projects` (the Vibe Coding projects) and `POST /api/update` with `POST /api/update/apply` (update from zip): loopback only, only `content-type: application/json`, or `application/zip` for the update zip and `application/zip` or `text/markdown` for a skill (a page from another site cannot send them without a CORS preflight to which the lens does not answer; `multipart/form-data` is refused precisely because it does not require one), with `Origin`, if present, equal to the dashboard's address and without reverse proxy headers.
- Imported skills are data, not programs: the zip (or the `SKILL.md`) is checked (safe names, no symlinks, limits on the number of files and on size, extraction into a folder that is always new) and copied into the library next to the database, never run. They are your own configuration, not OpenCode data, and like the presets they can be changed only from this computer.
- The update from zip runs the `install.sh` of the uploaded zip, with the user's permissions: it is the same as launching it from a terminal, and it can be requested only from this computer. The zip is read and extracted without executing anything until you confirm; the lens never downloads anything from the internet.
- It **does not proxy OpenCode's API** and never exposes its password. OpenCode's API includes sensitive endpoints, such as the list of credentials with secrets in clear, and they stay out of the dashboard.
- It does not save prompts, answers, tool input or output: only counts, times, model and tool names, and error messages. Before saving them it redacts them: `sk-…` keys, `Bearer <token>` and long token-like strings (32 characters or more) become `[redatto]`, the home folder becomes `~`; then it truncates them to 500 characters. It is a heuristic filter: a short secret or one of another shape may get through.
- It saves the **titles** of sessions, which are generated summaries of your prompt. `LENS_STORE_TITLES=0` excludes them.
- It saves each session's working folder, used for the breakdown by directory.
- The token is compared in constant time.
- An internal error answers with a generic 500; the log gets only the request's method and path, never the query (which may contain `?token=`).
- `GET /api/settings` never returns secrets; `LENS_OTLP_ENDPOINT` reaches only clients of this computer in full, the others get it obscured (credentials and query removed).
- Of prompts it saves only length and number of attachments; of shell commands only whether they were a `git commit`; of permissions the action and the number of resources, not the resources.
- The OTLP export, if active, sends the same data as the database (counts, times, names), never texts.
- The Security page reads, read-only, the DLP guards' audits and policies in OpenCode's folders (`LENS_SECURITY_DIRS`, `LENS_SECURITY_CONFIG_DIR`, only with the Security module on) without writing anything and without copying them into the database; over the network it shows only outcomes, tools and categories. See [sicurezza.md](sicurezza.md#who-sees-what).
- The MCP server (`opencode-lens mcp`) talks only to the lens's HTTP API (it reads, and reports preset deliveries: ids, never texts) and by default passes to the model counts and error classes, not texts, except for the text of the skills of the presets, which is yours: see [What reaches the model](#what-reaches-the-model).
