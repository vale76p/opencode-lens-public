# Metrics

## What the numbers mean

- **Step**: a call to the provider. It corresponds to an assistant message; retries reuse the same ID and are counted as attempts (`attempts`), not as extra steps.
- **Tokens**: OpenCode normalizes them like this (checked on OpenCode v2.0.26):
  - `input` = prompt **minus** the tokens read from cache;
  - `output` = completion **minus** reasoning;
  - the real prompt is therefore `input + cache read + cache write`. The “cache %” is `cache read / prompt`.
- **Cost**: computed by OpenCode from the model prices in the config (per million tokens). Reasoning is billed as output. For local models the cost is 0, unless you declare a price: see [configurazione.md](configurazione.md#prices-for-local-models).
- **Internal tasks**: title generation, compaction and other work OpenCode does without a visible step. Since schema v4 (OpenCode 2.0.32) the lens records them by type:
  - **title**: from the `session.usage.recorded` event with `source: "title"`. OpenCode leaves no message for the title and does not say which model generated it, so it exists **only live** and without a model;
  - **compaction**: from `session.compaction.ended` (or `failed`) live and from the `compaction` message when reading, with model, reason (automatic or manual) and usage. It is the total of the attempts: the `usage.recorded` of the same compaction are not added again;
  - **other**: the usual estimate, *session total − Σ steps − internal tasks already recorded*, as a delta with the synchronization date. It covers the lens being off or disconnected, old OpenCode versions and all the history before v4.

  An exact row that arrives after an estimate that already contained it **absorbs** it: Σ steps + Σ internal tasks stays equal to the session totals and nothing is counted twice. The total cost of the period includes internal tasks; cost and tokens **per model** (budget, table by dimension, trend) do not, not even the compactions whose model is known: the detail by type and by model is in `/api/summary` (`internal.byKind`, `internal.byModel`).
- **Latency**: duration of the step's last attempt, from start to end. Failed or still running steps do not enter the p50/p95 percentiles.
- **First token, tok/s and tool tail** (since schema v4, only for the OpenCode messages from mid-October 2026 on, those with `time.streamed`). For each step the lens saves three instants of the last attempt:
  - the **request** to the provider (`data.started` of `session.step.started`, `time.created` of the message);
  - the **first output**: text, reasoning or tool arguments (`session.text.started`, `session.reasoning.started`, `session.tool.input.started`). In the messages only the reasoning and tool parts have a time: if a step starts with text and the lens did not see it live, the first output is not known;
  - the **end of the stream** (`session.step.streamed`, `time.streamed`). It is not the first token: OpenCode writes it when the provider has finished answering, before waiting for the tools.

  From these three instants: **first token** = first output − request; **tok/s** = (output + reasoning) / (end of stream − first output), only for non-failed steps with at least 500 ms of stream and 20 tokens; **tool tail** = end of the step − end of the stream, that is how long the step waited for the tools after the model's answer. A repeated attempt resets first output and end of stream; an event of the previous attempt is ignored.
- **Tool duration**: execution only, without the time the model spends writing the arguments. From mid-October 2026 OpenCode records the tool start (`time.ran`, `session.tool.called` event) separately from the creation of the call (`time.created`, which is now the start of the arguments): the lens uses `ran`. Earlier data has no `ran` and its `created` is already the start of the execution, so for those it uses `created`. Calls still running do not enter the percentiles; the dashboard says over how many calls the duration is computed.
- **Interruption reason**: for an interrupted run OpenCode says why with `session.execution.interrupted` (`user` “by you”, `superseded` “superseded”, `inactivity` “for inactivity”, `shutdown` “OpenCode shutdown”), but does not write it in the `idle` message. So the reason exists only for runs seen **live** from schema v4 on; the others stay “interrupted”. With `shutdown` OpenCode writes no `idle`: that run stays open and merges with the next one (only the signal remains).
- **Run**: from the prompt (user or synthetic message) to the end of the answer. From mid-October 2026 OpenCode closes every run with an `idle` message that says the outcome (`succeeded`, `failed`, `interrupted`); a prompt sent while the run is in progress (`steer` or `queue`) stays inside that run. For messages in the previous format (without `idle`, without `time.streamed` on the steps) the lens infers the run from the prompt to the last assistant message before the next prompt, without an outcome (“no outcome”; “failed” if the last step errored). Cost, tokens and steps of a run include those of the subagents launched during the run. Only the runs of main sessions are counted: those of the subagents are already inside the run that launched them.
- **Prompts in the dashboard**: a prompt is a **run**, from the user's message to the `idle` message that closes the answer. Messages sent while the run is in progress stay inside it (their number is `prompts` in the list). Only main sessions count; tokens, cost, steps and tools of the subagents launched during the run are included, and internal tasks (titles, compaction) are **not**: they are not in a prompt's tokens.
- **Which prompt a step or a tool belongs to**: every step or tool belongs to the run if its instant (for a tool, that of its step) falls in `(end of the previous run of the same session, end of this run]`, on the session tree. “Interaction” (and the figures of `/api/activity`) instead uses the `[start, end]` window of the run: between an `idle` and the next prompt there is no work, so the numbers almost always match, but for old runs without a start or in edge cases they may differ slightly.
- **Running prompt**: prompts and runs are written only with the message synchronization, so the running prompt is recognized from steps and tools. There is a running prompt when the main session has activity after the end of the last run **and** either a step or a tool has been running for less than 30 minutes, or a permission is waiting, or the last step ended less than 5 minutes ago. It disappears by itself 1–2 seconds after the `idle`, when the synchronization writes the run. When a new run closes, the feed receives a “prompt completed” event (`kind: "run"`).
- **Context fill**: the prompt tokens of the last finished step (`input + cache read + cache write`) over the model's `limit.context`. The limit comes first from the OpenCode configuration, then from the service's model catalog (`GET /api/model`), reread at most every 10 minutes; if it is not found, the dashboard shows only the tokens. The catalog is checked like the events: a missing field appears among the API drifts (dashboard, `/api/status`, `/metrics`). The model's variant (`#xhigh`) is ignored in the search.
- **Prompts (messages)**: user messages in main sessions (the prompt an agent writes to launch a subagent does not count). Only the length in characters and the number of attached files and agents are saved; never the text. “During a run” are the prompts sent while the agent was working (`delivery: steer`), known only for prompts seen live.
- **Permissions**: permission requests (`permission.asked`) with the action (`shell`, `edit`, …) and the answer (`once`, `always`, `reject`). The **wait** is the time between request and answer: how long the agent stayed stopped waiting for you. OpenCode keeps only pending permissions, so the lens records them only while it is running.
- **Commits**: `git commit` (also `git -C dir commit`) successfully run by a shell tool (`shell`, `bash`). The command is not saved: only the fact that it was a commit. “Tokens per commit” is the total of the period divided by the commits.
- **Subagents**: child sessions (`parentID`). Every subagent session is linked to the `task`/`subagent` call that launched it; in sessions the lens sums the subagents (nested ones too) into the parent session. “Agent type” separates primaries and subagents in charts and tables.
- **Today**: the current budget day (from midnight, or from `LENS_RESET_HOUR`), tokens (internal tasks included), cost and steps, against the budgets `LENS_LIMIT_TOKENS`, `LENS_LIMIT_COST`, `LENS_LIMIT_STEPS`. The day's tokens have a bar with limit, 80% threshold and projection; week and month are in two mini bars of the same widget, only with the `_WEEKLY` and `_MONTHLY` budgets. Cost and steps appear only with a budget; the value turns yellow at 80% and red at 100%. The projection is linear (use so far ÷ elapsed time × 24 h) and appears after the first hour. The Today widget's comparison uses the average of the previous 7 budget days **up to the same hour** of the day (not the average of the whole day, which stays in the tooltip).
- **Calendar**: one square per day over the last 53 weeks, from Monday, in the chosen metric (tokens, cost, steps). The four color levels are the quartiles of the active days. The current streak counts the consecutive days with at least one step up to today.
- **Pruned days** (only with `LENS_RETENTION_DAYS`): the steps and tools older than the retention are no longer there as rows, but their per-day sums are. They count in the totals of `/api/summary` (of “All” and of a period chosen by hand that contains their midnight) and in `/metrics`; charts, breakdowns, sessions, prompts and latency show only the rows kept. See [Detail retention](configurazione.md#detail-retention).
- **tok/s** in the table by dimension: the median of the steps' tok/s (see above), with the median first token next to it. The old “Output tok/s”, output / whole step duration with the wait for the first token and for the tools inside, stays in the API as `outputTokensPerSec` but is no longer shown.
- **Colors**: the first 6 models (or agents, or providers) by *all-time* tokens have a fixed color, which does not change with the period. The others end up in “other” (grey). “Internal tasks” is purple.
- **Chart buckets**: hourly up to 2 days, daily up to 120 days, weekly (from Monday) beyond. In local time. With `LENS_RESET_HOUR` written with the final `Z` (for example `2Z`) the budget day is UTC and the hourly labels are UTC hours. On the day of the clock change the doubled hour sums two hours.

## Local API

All GET and all JSON, except the writes `POST /api/settings`, `POST /api/restart`, `POST /api/modules/notice`, `POST /api/modules/check`, `POST /api/dashboard`, `POST /api/presets`, `POST /api/skills`, `POST /api/skills/<id>`, `POST /api/skill-presets`, `POST /api/skill-loads`, `POST /api/vibe-projects`, `POST /api/update` and `POST /api/update/apply`. They accept `from`/`to` in ms epoch; `from=0` means “everything” and `from=day` the current budget day (from midnight or from `LENS_RESET_HOUR`, with `to` at the end of the day). Without `from` the period is the last week. The dashboard sends the language and the format it resolved in the `X-Lens-Lang` and `X-Lens-Locale` headers, and the texts of the answers meant for people (errors, descriptions, status) follow them; without the headers they are in Italian.

Now what is running is in the `opencode_lens_steps_running` and `opencode_lens_tool_calls_running` gauges; whoever used `finish="running"` or `status=~"pending|running"` must switch to these.
```promql
opencode_lens_today{kind="tokens"} / on(host) opencode_lens_daily_limit{kind="tokens"} > 0.8
```

### Counters that do not go down

The counters and summaries of `/metrics`, and therefore of the OTLP export, are all-time and are computed from the database rows. When the lens deletes rows (today only the retention of `LENS_RETENTION_DAYS`, tomorrow a migration) it always goes through `Store.deleteCompensated`: in the same transaction it compares the value of every series before and after the deletion and saves in `counter_offsets` what it lost, by name and labels (a summary as `<name>_sum` and `<name>_count`). `/metrics` adds the offset to the computed value, so:

- no series goes down because of a deletion;
- a series whose rows are all gone stays, with its last value, even if it was 0 (for example the cache tokens of a model that does not use the cache);
- new rows add up to the offset as before.

Without the retention `counter_offsets` stays empty and `/metrics` gives the same values as before.

The series with decimal values (the cost and the sums of duration, first token and tok/s) are floating-point sums, and a recomputation can round differently. So that they do not drop even in the last digit, their offset gets in addition a rounding margin computed for each series, proportional to the sum of the absolute values of its rows (and of its offset) and to their number. A series can therefore come out just above the exact count, with a relative overestimate of the order of 1e-9, never below. A series worth 0 has a margin of 0 and stays at 0; the integer series (counts, tokens, bytes) are exact.

They can still go down, as before:

- through a **correction** of the message read, which lowers a value that arrived live: in this case the lens follows the database, so the dashboard and `/metrics` stay in agreement;
- `opencode_lens_runs_total`, once, when updating a database older than v3: its migration removes the runs wrongly derived by 0.3.0.

Prometheus reads a drop as a reset; the OTLP export in `delta` sends 0 and starts again from the new value, without counting twice (see [OTLP export](#otlp-export)). IBM Bob's series have no offset: the retention does not delete Bob's data.

### Skill usage

`opencode_lens_skill_loads_total` and `opencode_lens_skill_preset_loads_total` count **completed** loads: failed ones stay in the database and in the Skill page, not in the counters. They are monotonic because `skill_uses` rows are never deleted, not even by the retention. Native skills (`origin="native"`) are there, even though the Skill page does not show them. The two metrics and the `skill_uses` table stay the core's: they keep filling even with the Skill module off (the only exception to “no metrics from an off module”); turning it off removes the page and the `/api/skill*` routes, not the counters.

- **Since when it counts.** `skill`, `activated` and the preset row of `lens-preset` have the whole OpenCode history (the reread after the migration to v5); the per-skill rows of `lens-preset` and `lens-prompt` start on the day of the update, because the MCP process writes them. That is why `/api/skill-usage` gives `since` per channel and the page writes “counts since …” and “Never used since …”.
- **The preset is its id.** Rows sit on the preset id: if a preset is deleted and recreated with another id, or `skill-presets.json` is edited by hand, the old rows stay on the old id and do not move. Lens's dialog does not change the id of an existing preset.
- Deliveries made while the lens is off are lost.

## OTLP export

With `LENS_OTLP_ENDPOINT` the lens sends the same metrics and, if `LENS_OTLP_TRACES` is not `0`, the traces to an OTLP/HTTP collector in JSON (`/v1/metrics`, `/v1/traces`): OpenTelemetry Collector, Grafana Cloud, Datadog, Honeycomb, SigNoz. Configuration in [configurazione.md](configurazione.md#otlp-export).

- **Metrics**: every `LENS_OTLP_INTERVAL` seconds. Counters are `cumulative` by default; with `LENS_OTLP_TEMPORALITY=delta` (Datadog) the difference from the previous export is sent. Summaries have `_sum` and `_count`.
- **Traces**: one trace per root session. Every run is an `opencode.run` span, every step an `opencode.llm` span under its run (OpenInference and GenAI attributes: model, provider, tokens, cost, finish), every tool an `opencode.tool.<name>` span under its step. Since schema v4 steps with streaming timings also have `opencode.step.ttft_ms` and `opencode.step.output_tokens_per_second`, and interrupted runs with a known reason `opencode.run.interrupt_reason`. A run's span is sent only once, when the run is synchronized: usually the interruption event arrives first and the reason is there, but if it arrives after sending it stays in the database and in the APIs and not in the span already exported (it is not sent again, because many backends would save a second span with the same id). The runs of a subagent are under the `task`/`subagent` call that launched it. Span ids derive from OpenCode's: a new send after an error creates no duplicates.
- A run is sent when the sync has recorded it, that is after its end, together with all its steps and tools. Runs are taken in recording order: even one synchronized late goes out. At the first start the lens sends the last hour, not all the history. A step outside any run (session still in progress) goes out with the run when it closes.
- In `delta` the base for the differences is updated only after a send accepted by the collector and is saved in the database: a failed send is recovered at the next one, a restart does not resend the history. The base is keyed by name and labels in canonical order: a series that `/metrics` recreates from `counter_offsets`, with the labels in another order, does not look new and is not resent whole; the state saved by a previous version is converted on load, so the update resends nothing. If a series drops (with `counter_offsets` this happens only for a backfill correction) 0 is sent and the base realigns to the new value.
- No prompt, answer, input or output of tools leaves the lens, as for the database. Error spans carry only the error type, not the message.
- The state of the export (last send, spans sent, last error) is in the **Settings** page.

When a counter can still go down, and what is left of the series with the retention, is in [Counters that do not go down](#counters-that-do-not-go-down).
